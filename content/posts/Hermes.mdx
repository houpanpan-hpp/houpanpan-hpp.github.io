## 背景

2026 年以来，AI 行业的迭代速度开始压缩到按周计算。近几个月出现的新框架、新模型和新产品，密度已经超过过去好几年。

Hermes Agent 就是其中一个代表项目。它由 Nous Research 在 2 月底推出，是一个开源 Agent 项目。发布后，它在 GitHub 上快速积累了 4 万颗 Star，版本更新速度也超过不少商业化 Agent 产品。

Hermes 官网对它的定位很明确：它不是绑定在 IDE 里的编程 Copilot，也不是封装单一 API 的聊天机器人外壳；它是一个部署在服务器上的自主智能体，能够记住所学内容，运行时间越长，能力越强。

这句话点出了 Hermes 的两个核心特征：

- Persistent：持久运行。
- Self-Evolving：自进化。

![](/HermesPic/image.png)

功能上，Hermes 支持 40 多款内置工具，兼容多种主流大语言模型，并内置 Cron 调度器来执行复杂定时任务。交互上，它和 OpenClaw 类似，支持通过第三方消息平台访问，因此可以覆盖更多使用场景。

Hermes 的热度已经接近甚至超过 OpenClaw。很多用户开始从 OpenClaw 迁移到 Hermes，而 Hermes 官方也支持从 OpenClaw 无缝迁移。OpenClaw 才火了两个多月，后继者就已经把节奏推到了下一个阶段。

这个系列前两篇已经分析过 OpenClaw 和 Claude Code。本文延续同一套框架，从 Prompt Engineering、Context Engineering、Harness Engineering 三个维度分析 Hermes Agent，但会增加一个新重点：Hermes 如何实现自进化。

![](/HermesPic/image-1.png)

OpenClaw 和 Claude Code 也具备持久运行能力。Hermes 的差异在于，它尝试通过机制设计，让 Agent 具备长期记忆、持续学习和自主优化能力。

研究 Hermes 后可以看到，它站在 OpenClaw 和 Claude Code 的肩膀上。它的 Prompt 结构、Context 管理和 Harness 设计都有相似之处。本文不重复展开这些共性，而是聚焦 Hermes 与前两者不同的地方：它如何在继承成熟工程设计的基础上，把「自进化」做成系统能力。

## Self-Evolving：内外双路径驱动的自进化

Hermes Agent 的自进化主要依赖两条路径：

- 自动 Skill 生成：轻量、即时生效，用于沉淀日常任务经验。
- RL 训练：手动触发，直接改变模型权重，用于提升模型在特定领域的能力。

这两条路径构成了 Hermes 的自进化闭环。Skill 负责把经验外挂到系统里，RL 负责把经验内化到模型里。

![](/HermesPic/image-2.png)


## 动态 Skill 生成：从一次性执行到经验沉淀

OpenClaw 的上下文管理主要服务当前会话稳定性。它通过压缩上下文防止 Context Window 爆炸，通过 Memory 记住关键事实或日常事件，减少后续对话遗忘。

这套设计解决了 Context 容量问题，但没有解决执行经验沉淀问题。Agent 完成一个任务后，过程中走过的弯路、犯过的错误、自我纠正过程和人工干预经验，很难自动保存下来。下一次遇到类似任务，它仍然会从头探索。

你可以主动要求 OpenClaw 把错误经验保存到 Memory 或 Skill 里，但系统不会自动做这件事。即使写入 Memory，Markdown 文件里通常也只记录重点事项和用户习惯，不会记录完整执行细节。

换句话说，OpenClaw 不能主动从历史交互中学习。它的能力上限主要来自基座模型、静态提示词和静态 Skill。

Hermes 用动态 Skill 沉淀机制解决这个问题。每次完成复杂任务，尤其是经历曲折路径或人工干预的任务后，Hermes 会启动复盘流程。它回看执行轨迹，提取关键步骤、踩坑点、有效纠错方法和人工验证过的实践，然后把这些经验抽象成一个结构化 Skill 文件包。

这里的关键变化是：Skill 从静态调用变成动态生成。

OpenClaw 和 Claude Code 也支持 Skill，但它们的 Skill 通常由用户或开发者预先编写，或从官方、第三方 Skill 库安装。它更像传统 App 模式：先发布，后安装，再运行。安装完成后，Skill 只有在人为更新时才会变化。

Hermes 把 Skill 变成一种可进化资产：

- 自动生成：Hermes 可以基于自身 Agent 运行轨迹生成新的 Skill。
- 持续优化：后续任务中出现更优路径、边界情况或新踩坑点时，Hermes 会更新已有 Skill。
- 持续积累：对话越多，沉淀出的 Skill 越多，Agent 的能力库也越丰富。

当 Hermes 下次遇到类似问题时，它不必从零探索，可以读取并复用已经沉淀的 Skill。每一次执行都会转化为后续任务的经验资产。

### 触发机制

在根目录的 `run_agent.py` 中，Hermes 设置了一个技能催促计数器：

- `_iters_since_skill`：记录距离上次使用 `skill_manage` 工具经过了多少轮。
- `_skill_nudge_interval = 10`：当 Agent 连续工作 10 轮都没有创建或修改技能时，系统会提醒 Agent 是否需要把刚才学到的经验整理成 Skill。

### 后台审查 Agent

主 Agent 完成对用户的回复后，前台交互已经结束。Hermes 会通过 `_spawn_background_review` 在后台异步启动一个审查 Agent，专门复盘刚结束的对话。

这个后台 Agent 不干扰用户体验，只负责从三个维度审查交互：

- 记忆审查：`_MEMORY_REVIEW_PROMPT` 判断这段对话是否包含值得长期保留的经验或事实，并写入记忆库。
- 技能审查：`_SKILL_REVIEW_PROMPT` 分析当前任务路径是否具备通用性，是否值得抽象为 Skill。
- 综合审查：`_COMBINED_REVIEW_PROMPT` 反思执行过程中的优化空间和潜在错误模式。

这形成了一种「前台即时响应，后台异步进化」的设计。用户看到 Agent 完成回复，后台审查 Agent 则继续整理经验，为后续任务积累数据。

## RL 训练闭环：把经验写进权重

动态 Skill 生成像记笔记。它见效快、可解释，也方便人工干预和纠偏。但它仍然是一种外挂式进化：无论 Agent 积累多少 Skill，底层模型权重都没有变化。

对于需要极致性能或垂直领域能力的场景，Context Engineering 和外部知识检索仍然有上限。Hermes 因此引入第二条路径：基于强化学习的模型训练闭环。

如果 Skill 生成是在「记笔记」，RL 训练就是在「练模型」。它通过改变模型权重，把经验内化为模型能力。这个方向和 Andrej Karpathy 的 AutoResearch 有相似之处，都尝试用自动化流程在单 GPU 上做 RL 训练。Hermes 的工程闭环更完整。

Hermes 在 README 中把这套框架称为 Research-Ready，而不是简单叫 Model Fine-Tuning 或 Model Training。原因在于，它不只包含训练动作，还覆盖数据合成、质量筛选、RL 训练环境构建、小规模实验、正式训练和自动评估。

整个 RL 训练流程可以拆成四个阶段：

1. 任务定义：用户指定训练目标，例如提升数学推理能力或优化某类业务问题成功率。系统根据目标选择训练数据、Benchmark，或要求用户提供数据集。
2. 轨迹捕获与批量数据合成：Hermes 通过 `batch_runner.py` 自动合成 Agent 运行轨迹，筛选高质量样本，并转换为 ShareGPT 格式。它通常使用强模型作为 Teacher Model 生成示范数据，再创建隔离的 RL 训练环境和超参数配置。
3. 渐进式训练与自动评估：Hermes 先用小规模数据集做实验，验证可行性后再启动正式训练。训练结束后，系统自动评估指标。如果效果不足，反馈信号会指导下一轮参数或数据调整；如果效果达标，系统固化该版本模型。
4. 领域局部最优：RL 奖励机制让模型针对特定场景的正确行为获得正向反馈，从而学会该领域的专有逻辑，在特定任务上接近或超过通用基座模型。

## Agent 轨迹组织

Agent 轨迹（Trajectory）指 Agent 完成一次任务的完整对话记录，包括系统提示词、用户请求、Agent 的思考和行动、工具调用和工具结果。

在 `agent/trajectory.py` 中，Hermes 可以把 Agent 轨迹转换为 ShareGPT 格式。整个自进化 Pipeline 使用这种统一格式：

```json
[
  { "from": "system", "value": "你是 Hermes Agent..." },
  { "from": "human", "value": "帮我部署这个应用" },
  { "from": "gpt", "value": "好的，我先检查环境..." },
  { "from": "tool", "value": "<tool_call>execute_code(...)</tool_call>" },
  { "from": "tool", "value": "<tool_response>成功</tool_response>" },
  { "from": "gpt", "value": "部署完成！" }
]
```

ShareGPT 格式已经被 LLaMA-Factory、FastChat、OpenChat 等训练框架广泛支持。`"from": "gpt"` 只是历史遗留字段，不代表只能训练 GPT 模型。训练框架会把它映射到具体模型 Chat Template 中的 assistant token。

Hermes 通过三个核心函数保证训练数据质量：

- `save_trajectory`：以追加模式把 Agent 运行轨迹写入 JSONL 文件，实现增量积累。
- `convert_scratchpad_to_think`：把内部 `<REASONING_SCRATCHPAD>` 标签转换为通用 `<think>` 格式，适配 CoT 训练要求。
- `has_incomplete_scratchpad`：检查推理标签完整性，过滤因截断导致的残缺样本。

最终输出包含两类文件：

- `trajectory_samples.jsonl`：成功完成的轨迹。
- `failed_trajectories.jsonl`：失败轨迹。

每条 JSONL 记录结构如下：

```json
{
  "conversations": [],
  "timestamp": "2025-04-11T10:30:00",
  "model": "anthropic/claude-4.6-opus",
  "completed": true
}
```

## 批量数据生成

`batch_runner.py` 是 Hermes 自进化的数据工厂。它并行处理大量提示词，为每个提示词运行一次完整 Agent 对话，并收集轨迹。

它的主要流程包括：

- 准备提示词：人工准备 JSONL 格式的提示词文件，例如 `{ "prompt": "请帮我搜索 AI 领域的最新进展" }`，也可以从 GSM8K、HumanEval 等 Benchmark 中采集。
- 并行处理：`batch_runner.py` 用线程池处理提示词，每条提示词创建一个独立 Agent 实例。
- Teacher Model 生成：默认使用 `anthropic/claude-opus-4.6` 作为 Teacher Model，执行包含工具调用、推理和搜索的完整 Agent 对话。
- 录制轨迹：把 Teacher Model 的完整执行过程转换为 ShareGPT 格式训练数据。
- 工具集随机采样：系统随机采样不同工具组合，让训练数据覆盖更多工具搭配场景，避免模型死记一种配置。
- 零推理过滤：`_extract_reasoning_stats` 会统计 `<REASONING_SCRATCHPAD>` 和 `reasoning` 字段出现次数。如果两者都为零，系统丢弃样本，因为这说明 Agent 没有显式推理过程。

Hermes 还支持 Hindsight-Guided On-Policy Distillation（OPD）。这是一种更精细的 Teacher-Student 机制，基于 Princeton 大学 2026 年 OpenClaw-RL 论文《OpenClaw-RL: Train Any Agent Simply by Talking》。具体实现可查看 `environments/agentic_opd_env.py`。

### SWE 任务数据生成

除了通用的 `batch_runner.py`，Hermes 还有 `mini_swe_runner.py`，专门处理 SWE Benchmark 软件工程任务。

| 文件 | 用途 | 任务类型 | 完成信号 |
| --- | --- | --- | --- |
| `batch_runner.py` | 通用数据批量生成 | 任意提示词 | 对话自然结束 |
| `mini_swe_runner.py` | SWE Benchmark 任务 | 代码修复或实现 | `echo "MINI_SWE_AGENT_FINAL_OUTPUT"` |

## Agent 轨迹压缩

原始轨迹可能包含几十万个 Token。一次复杂对话可能调用十几次工具，直接用于 RL 训练并不现实。Hermes 通过 `trajectory_compressor.py` 把轨迹压缩到可控大小。

核心配置如下：

```python
@dataclass
class CompressionConfig:
    tokenizer_name = "moonshotai/kimi-k2.5"  # 精确 Token 计数器
    target_max_tokens = 15250      # 压缩后的目标上限
    summary_target_tokens = 750    # 摘要的 Token 预算
    protect_last_n_turns = 4       # 保护最后 4 轮对话
    summarization_model = "google/gemini-3-flash"  # 轻量摘要模型
    max_concurrent_requests = 50   # 并发摘要请求数
```

压缩流程分为几步。

首先，系统使用 HuggingFace 的 `AutoTokenizer` 对原始轨迹做精确 Token 计数，避免粗略估算。如果轨迹长度已经低于目标上限，系统跳过压缩，保留完整信息。

如果需要压缩，系统会把对话划分为三个区域：

- 头部保护区：保留第一条系统指令、第一条人类消息、第一条 GPT 回复和第一次工具交互。这些内容定义任务起点，不能压缩。
- 尾部保护区：保留最后 4 轮对话。这些内容包含最终结论、输出结果和验证信息，是评估任务完成度的关键信号。
- 中间压缩区：压缩大量中间步骤、工具调用和纠错过程。这部分记录探索路径，但冗余多。

系统随后计算需要节省的 Token 数，从中间压缩区起始位置开始累积待压缩内容，直到满足目标。Hermes 把这些片段发给轻量模型，例如 Gemini Flash，要求它生成以 `[CONTEXT SUMMARY]:` 开头的摘要。

最后，系统把头部保护区、摘要、尾部保护区重新拼接，形成一条结构完整但体积更小的新轨迹。

头部保护任务定义，尾部保护训练信号，中间用摘要保留探索脉络。Hermes 用这种方式平衡数据质量和训练成本。

## RL 强化学习训练

`rl_cli.py` 是 Hermes 的 RL 训练入口。它连接数据、环境和训练流程，引导 Agent 完成标准化训练。

关键配置如下：

```python
RL_MAX_ITERATIONS = 200
DEFAULT_MODEL = "anthropic/claude-opus-4.6"
RL_TOOLSETS = ["terminal", "web", "rl"]
```

Hermes 把复杂的模型调优过程抽象为一套可复现流程，减少配置错误造成的资源浪费。

### Discover & Inspect

用户先通过 `rl_list_environments()` 查看可用训练环境模板。选定目标后，进入 Inspect 阶段，阅读环境文件中的关键逻辑：

- `load_dataset()`：数据加载机制。
- `score_answer()`：评分函数定义。
- `get_next_item()`：数据迭代方式。
- `system_prompt` 和 `config_init()`：环境提示词与初始化配置。

用户也可以通过终端探索 HuggingFace 数据集，确认训练数据的分布和质量。

### Create & Configure

用户复制并修改合适的环境模板，再用 `rl_select_environment` 和 `rl_edit_config` 定制训练参数。这个阶段决定模型在什么规则下训练。

### Test & Train

正式投入算力前，Hermes 要求执行 `rl_test_inference`，验证环境配置和推理链路。确认无误后，用户调用 `rl_start_training` 启动训练任务，并用 `rl_check_status` 监控进度。

由于训练任务异步执行，状态检查建议至少间隔 30 分钟，避免频繁请求增加系统负载。

### Evaluate

训练结束后，系统通过 `rl_get_results` 获取模型产物，并结合 WandB 指标分析损失曲线、奖励得分等指标。用户据此判断模型是否达到预期，再决定接受该版本，或回到配置阶段继续迭代。

## GRPO 算法思路

Hermes 使用 GRPO（Group Relative Policy Optimization）强化学习算法。GRPO 来自 DeepSeek R1 论文。Hermes 中的相关 Skill 位于 `/skills/mlops/training/grpo-rl-training/SKILL.md`。

GRPO 的思路很直接：对同一个问题，让模型生成 8 到 16 个不同回答；奖励函数给每个回答打分；模型学习提高高分回答概率，降低低分回答概率。

GRPO 的优势是不用单独训练 Reward Model，而是直接使用规则化奖励函数。相比训练奖励模型，这条路径成本更低，也更容易控制。

Hermes 使用多维组合奖励，而不是只看单一指标。`basic_grpo_training.py` 中的核心奖励维度如下：

| 维度 | 权重 | 衡量内容 |
| --- | --- | --- |
| 正确性 | 2.0 | 最终答案是否正确 |
| 格式规范 | 0.5 | 是否遵循 `<reasoning>...<answer>` 结构 |
| 渐进格式 | 0 到 0.5 | 部分符合格式也给分，例如只写了开标签 |

`/skills/mlops/training/grpo-rl-training/SKILL.md` 中还总结了奖励函数设计原则：

- 组合 3 到 5 个奖励函数，每个函数负责一个维度。
- 正确性权重最高，格式权重次之。
- 保留部分分，避免把接近正确的样本全部打成 0。
- 先单独测试每个奖励函数，再合并使用。

在 Hermes 的 RL 环境中，奖励函数不只做字符串匹配。通过 `ToolContext`，奖励函数可以执行终端命令、读取文件、访问网络、使用浏览器。这意味着奖励函数可以做真实验证。训练 Agent 写代码时，奖励函数可以直接编译运行代码来判断答案。

## 为什么不直接从用户数据中学习

很多营销解读会说 Hermes 可以自动读取用户对话数据训练模型，从而用着用着变聪明。源码层面的设计并不是这样。

Hermes 的 RL 训练数据主要来自 Teacher Model 合成数据或 Benchmark 构造数据。它的核心目的也不是直接从用户那里学习，而是做知识蒸馏：把 Claude Opus 这类大模型的 Agent 能力压缩到 Qwen 3B、4B 这类小模型中。

这样做有三个价值：

- 降本：Claude Opus API 调用成本高，本地小模型成本低。
- 提速：小模型推理速度更快。
- 合规：部分场景不能调用外部 API，本地模型可以让数据不出机器。

通过 RL 奖励机制，开源模型有机会在特定领域的 Agent 能力上接近甚至超过更大闭源模型。再叠加自动生成 Skill 的外部进化层，Hermes 可以在具体场景中获得更好的工作效果。

从理论上说，如果要实现「越用越聪明」的体验，确实需要收集高质量用户对话轨迹用于训练。但 Hermes 不建议直接这么做，原因主要有两个：

- 隐私风险：用户对话可能包含敏感信息，用户未必愿意把这些内容训练进模型。
- 质量风险：用户对话质量参差不齐，直接训练可能降低模型质量。按过往模型训练经验，直接用历史对话训练模型，很容易把模型训坏。

如果用户确实需要基于历史对话轨迹提升模型能力，可以把历史对话作为数据源人工导入到批量数据构造阶段，再由 Teacher Model 参考这些数据合成样本，并做质量把关，最后交给 RL 训练。

到这里，Hermes 的自进化部分可以总结为两层：

- 动态生成 Skill 解决即时纠错和沉淀复用。
- RL 训练闭环解决模型能力提升。

两者结合，构成 Hermes 的完整自进化体系。

## Prompt Engineering：模型异构与迁移兼容

Hermes 的 Prompt Engineering 延续了主流动态拼装范式。它先定义 Agent 身份，再加载 `SOUL.md` 等角色文件，最后注入工具调用指南、工具名称和工具描述。

基础结构和 OpenClaw、Claude Code 高度相似。Hermes 的差异不在结构复刻，而在对不同模型行为差异和生态兼容性的处理。

### 工具使用强制指导

不同基座模型对工具调用的主动性不同：

- Claude 训练时就强调工具使用，通常不需要额外提醒。
- GPT 或 Codex 容易只说不做，需要明确提示必须执行工具。
- Gemini 或 Gemma 需要提醒使用绝对路径、编辑前先读文件、独立操作并行调用工具。

Hermes 会根据当前模型动态注入指令补丁。对容易偷懒的模型，它强调「执行而不是描述」。对工具顺序敏感的模型，它强调路径、读取和并行调用规范。

配置项 `agent.tool_use_enforcement` 支持以下值：

```text
"auto"              # 默认，根据模型名自动判断
true                # 强制注入
false               # 不注入
["gpt", "gemini"]   # 只对列表中的模型注入
```

GPT 专属指导包括：

- 写文件、执行代码、终端命令、网页搜索等场景必须用工具。
- 不能编造文件路径或 API 地址。
- 修改文件后要确认，测试代码后要验证输出。

Gemini 和 Gemma 专属指导包括：

- 始终使用绝对路径。
- 编辑前先读取文件确认内容。
- 多个独立操作要并行调用工具。

这些提示词看起来属于 Prompt Engineering，但它也承担了一部分 Harness 约束功能：通过提示词弥补模型行为差异。

### 兼容各类 AI 产品生态

Hermes 的另一个优势是迁移成本低。它在 System Prompt 拼装逻辑中保留了对主流 Agent 框架配置文件的兼容。

Hermes 兼容 OpenClaw 生态，可以直接读取并解析 `AGENT.md`、`SOUL.md`、`USER.md` 等核心配置文件。用户可以把已有 OpenClaw 工作流迁移到 Hermes。

Hermes 也兼容 AI Coding 主流规范。它支持读取 `CLAUDE.md`、`.cursorrules`、`.cursor/rules/*.mdc` 等描述文件，因此能快速融入 Cursor、Claude Code 等编码助手已有的项目规则。

Hermes 还兼容多平台 IM 协议。针对 WhatsApp、Slack 等即时通讯平台，它内置了相应适配提示词，让 Agent 在不同交互界面中保持合适语气和行为。

因此，Hermes 的 Prompt Engineering 更像一个连接不同模型和不同平台的枢纽。它用动态适配解决模型短板，用生态兼容降低迁移成本。

Hermes 在 System Prompt 动态拼装方面与 OpenClaw、Claude Code 很接近：先定义 Agent 身份，再加载人设、工具指导、时间戳、Gateway 信息、Memory、模型信息等。这里不重复展开。

## Context Engineering：比例阈值压缩与记忆持久化

Hermes 的 Context Engineering 目标和 OpenClaw、Claude Code 一致：处理对话轮次增加、工具调用累积带来的 Context Window 溢出问题。

它通过上下文压缩、Memory 增强、关键信息注入和持久化，保证 Agent 在长程任务中的稳定性和连贯性。

在持久化存储上，Hermes 选择和 OpenClaw 相同的 SQLite。这个轻量数据库可以存储长期 Memory 数据和历史对话记录，为 Agent 提供稳定的长期记忆。

### 压缩：上下文动态阈值

Hermes 和 OpenClaw 在实时上下文压缩触发逻辑上有差异。

OpenClaw 常用绝对阈值触发。例如上下文总容量是 20K，边界预留 2K，Token 数达到 18K 时触发压缩。这种方式简单，但不同模型窗口大小不同，配置需要频繁调整。

Hermes 使用相对阈值触发。`agent/context_compressor.py` 监控当前上下文占模型总窗口的比例。例如上下文长度达到模型总窗口 50% 时，系统触发压缩：

```text
context_length = 200,000 tokens
threshold_percent = 0.50
threshold_tokens = 200,000 x 0.50 = 100,000 tokens

当前对话 Token 数 >= 100,000，触发压缩
```

这种比例机制对不同窗口大小的模型更友好。无论底层模型是 200K 窗口还是 32K 窗口，Hermes 都能根据剩余空间状态决定何时压缩。

具体裁剪时，Hermes 采用和 OpenClaw 类似的「头尾保留，中间摘要」策略：

- 头部保护：保留系统指令、初始任务定义等关键引导信息。
- 尾部保护：保留最近几轮对话，保证短期上下文连贯。
- 中间压缩：裁剪中间冗长工具调用和推理步骤，并用 LLM 生成摘要替代原始细节。

Hermes 通过压缩和裁剪避免上下文爆炸，同时保留任务执行关键脉络。

实时上下文压缩和离线轨迹压缩可以这样对比：

| 特性 | 上下文实时压缩 | 离线 Agent 轨迹压缩 |
| --- | --- | --- |
| 运行时机 | 对话进行中 | 对话结束后 |
| 目的 | 保持对话可继续 | 准备高质量训练数据 |
| Token 目标 | 降到上下文窗口 50% 以下 | 精确到 15250 |
| Token 计数 | 粗略估算，约 4 字符 1 Token | HuggingFace Tokenizer 精确计数 |
| 总结器 | 同模型或配置模型 | Gemini Flash 等轻量模型 |
| 保护策略 | 保留前 10 条和尾部动态内容 | 保留首轮系统、人类、助手、工具交互和最后 4 轮 |

### Memory：内外双驱的混合架构

Hermes 的 Memory System 采用「内部静态存储 + 外部动态扩展」双层架构。OpenClaw 更偏单一内部记忆机制。Hermes 这套设计兼顾记忆稳定性和生态开放性。

内部记忆主要基于文件。Hermes 通过 `MEMORY.md`、`USER.md` 等 Markdown 文件维护 Agent 的核心认知。

这些文件主要记录长期、相对静态的事实性知识，例如用户偏好、项目背景和关键约束。它不像日志那样记录每一轮交互，而是提炼关键信息，方便人工编辑。

从记忆召回内容时，Hermes 会用特殊标签包裹，避免模型把记忆误判为新用户输入：

```xml
<memory-context>
[System note: The following is recalled memory context,
NOT new user input. Treat as informational background data.]

用户偏好使用 Python 和 TypeScript。
上次会话中讨论了 React 组件架构。
</memory-context>
```

对话持久化方面，Hermes 和 OpenClaw 都使用 SQLite，但用途不同。Hermes 直接用 SQLite 存储每日对话历史，而 OpenClaw 更偏向存储 Memory 的 Chunk 索引。

这样做有两个好处：

- 结构化数据资产：对话历史可查询、可索引，后续可以按主题检索或按时间回溯。
- 支撑自进化闭环：SQLite 中的高质量对话轨迹可以作为生成 Skill 和 RL 训练的数据源。

外部记忆方面，Hermes 支持接入第三方记忆服务，例如 Mem0、Honcho、Hindsight、Supermemory 等。通过这些服务，Hermes 可以复用向量检索、语义关联和跨会话记忆能力。

外部记忆还带来迁移能力。用户记忆资产不必锁定在某个 Agent 框架内，可以通过标准化接口流转。

内部记忆保证基础档案稳定，外部记忆提供更大的召回空间。这种混合架构让 Hermes 既保留本地可控性，也具备扩展能力。

### 上下文注入：从工具调用到即时挂载

Hermes 的上下文注入（Context Injection）体现了它对交互效率的重视。它引入了 `@` 语法，让用户快速挂载资源。

传统模式是被动检索：用户发出指令，Agent 识别意图，调用 `read_file` 或 `browser_use` 等工具，获取结果，再拼接到上下文。这需要多轮推理和工具执行。

Hermes 模式是主动注入：用户通过 `@` 直接指定资源，系统立即把内容注入当前 Prompt 上下文。

| 语法 | 作用 | 效果 |
| --- | --- | --- |
| `@file:main.py` | 读取整个文件 | 注入 `main.py` 完整内容 |
| `@file:src/utils.py:10-20` | 读取指定行 | 只注入第 10 到 20 行 |
| `@folder:src/` | 列出目录树 | 显示文件大小和修改时间 |
| `@diff` | Git 未暂存更改 | 等同于 `git diff` |
| `@staged` | Git 已暂存更改 | 等同于 `git diff --staged` |
| `@git:3` | 最近 3 次提交 | 包含完整补丁 |
| `@url:https://...` | 抓取网页内容 | 转为 Markdown |

这套机制把工具调用变成上下文预加载。模型在接收用户指令时就已经拥有相关背景，减少工具调用等待时间，也降低多轮交互带来的 Token 消耗。

## Harness Engineering：约束与运行保障

Harness Engineering 负责 Agent 运行保障、异常处理、安全管控和扩展能力。

Hermes 在底层逻辑上和 OpenClaw 相似，但它在错误恢复、子 Agent 隔离和插件生态上做了更细的工程处理，目标是构建灵活、稳定的生产级运行环境。

### 全生命周期 Hook 机制

Hermes 和 OpenClaw、Claude Code 一样，提供完整生命周期 Hook 系统。开发者可以在 Agent 运行关键节点注入自定义逻辑或约束，例如日志记录、权限校验和业务规则。

| Hook | 触发时机 |
| --- | --- |
| `on_agent_start()` | Agent 初始化时 |
| `on_tool_call()` | 工具执行前 |
| `on_tool_result()` | 工具返回后 |
| `on_agent_end()` | Agent 关闭时 |
| `on_turn_start()` | 每轮开始时 |
| `on_pre_compress()` | 压缩前，可在消息被丢弃前提取信息 |
| `on_memory_write()` | 写入内置记忆时 |
| `on_delegation()` | 子 Agent 完成任务后 |
| `on_session_end()` | 会话结束 |

### 结构化错误分类与自愈体系

长程任务中，系统报错很容易让 Agent 中断或陷入循环。Hermes 建立了 14 种错误分类，不再笼统处理 Error，而是把接口超时、参数错误、权限拒绝、资源不足等异常标准化。

针对每类错误，Hermes 预设恢复策略。当异常发生时，系统识别错误类型，并执行重试、降级或修正操作。

`agent/error_classifier.py` 中列出的错误类型如下：

| 错误类型 | 含义 | 典型场景 |
| --- | --- | --- |
| `auth` | 认证失败 | API Key 无效 |
| `auth_permanent` | 永久认证失败 | 账号被封禁 |
| `billing` | 账单问题 | 额度用完 |
| `rate_limit` | 请求过多 | 被限流 |
| `overloaded` | 服务器过载 | 服务器忙 |
| `server_error` | 服务器错误 | 5xx 错误 |
| `timeout` | 请求超时 | 网络问题 |
| `context_overflow` | 上下文溢出 | 消息太长 |
| `payload_too_large` | 请求体太大 | 413 错误 |
| `model_not_found` | 模型不存在 | 模型名错误 |
| `format_error` | 请求格式错误 | 参数问题 |
| `thinking_signature` | 思考签名错误 | Anthropic 特有 |
| `long_context_tier` | 长上下文限制 | Anthropic 特有 |
| `unknown` | 未知错误 | 需要重试 |

### 受控的子 Agent 机制

面对复杂任务，Hermes 支持把部分工作委托给 Sub-Agent 并行处理。为了避免递归委派造成资源爆炸或逻辑混乱，Hermes 对子 Agent 做了沙箱限制：

- 子 Agent 不能再次创建新的子 Agent。
- 子 Agent 不能向主 Agent 反向提问。
- 子 Agent 不能访问主 Agent 或其他子 Agent 的完整上下文和记忆库。
- 子 Agent 只能获取当前任务需要的上下文片段。

`tools/delegate_tool.py` 中的安全限制如下：

```python
DELEGATE_BLOCKED_TOOLS = {
    "delegate_task",     # 防止递归委派
    "clarify",           # 防止嵌套提问循环
    "memory",            # 防止操纵记忆
    "send_message",      # 防止消息劫持
    "execute_code"       # 防止代码执行权限升级
}

MAX_CONCURRENT_CHILDREN = 3
MAX_DEPTH = 2
```

这种限制保证任务分解的单向性，也让多个子 Agent 可以并行执行、互不干扰。

### 插件系统与生态扩展

Hermes 内置插件系统。第三方开发者可以通过标准接口扩展能力，而不需要改核心代码。前文提到的 Mem0、Hunter 等外部记忆组件，以及自定义工具和 Hook，都可以以插件形式存在。

这种解耦设计降低了生态贡献门槛，也让 Hermes 可以更快集成社区能力。

### 多层安全护栏

生产环境里，安全性必须作为硬约束。Hermes 构建了多层防御体系：

- 防 Prompt 注入：检测并拦截恶意提示词注入，防止用户绕过系统限制。
- Skill 安全扫描：动态生成或外部引入 Skill 时，系统在加载前做静态代码分析和安全扫描，避免恶意逻辑或敏感操作进入运行环境。

Hermes 的 Harness Engineering 本质上是一套运行管控体系。它把监控、自愈、隔离、扩展和安全组合在一起，用标准化错误处理和子任务隔离提升稳定性，用插件生态和安全护栏平衡灵活性与合规性。

## 总结

Hermes 不是凭空出现的项目。它在基础架构、System Prompt 拼装逻辑和上下文管理上延续了 OpenClaw、Claude Code 的成熟设计。

它的核心突破在于补上了传统 Agent 的一个缺口：Agent 无法主动学习和进化。

传统 Agent 每次任务执行往往从零开始。上一次走过的弯路、人工纠错经验和验证过的方法，通常会随着会话结束消散。Hermes 通过动态 Skill 沉淀和 RL 闭环训练，打通了从任务执行到经验记录、从 Skill 抽象到模型再训练的数据链路。

可以把 Agent 发展阶段分成三类：

- 早期 Agent：被动响应用户指令，一问一答，无法执行复杂长周期任务。
- 自主 Agent：OpenClaw、Claude Code 等系统可以自主规划路径、调用工具，独立完成复杂任务。
- 自进化 Agent：Hermes 进一步让 Agent 在执行中学习，在学习中增强。

从自主到自进化，是当前 AI 系统架构演进的重要方向。更强基座模型和更优自进化架构结合，会继续缩短想法到实现之间的距离。

Hermes 的价值不只在于它提供了一个新的 Agent 产品，更在于它把「经验沉淀」和「模型训练」这两件事连接成工程闭环。对于正在构建长期运行、自主执行、持续优化 Agent 系统的团队，这套思路值得研究。
